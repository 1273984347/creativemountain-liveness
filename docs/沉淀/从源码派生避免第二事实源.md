# 从源码派生，避免第二事实源

## 判据

凡是**字段清单 / 枚举取值 / 校验规则 / 构建参数**，一律不得在多处手抄；
必须有一个**从源码派生**的解析器，其余位置引用它。

症状（任一命中即视为第二事实源）：

- 同一批字段名/正则/枚举在两个及以上文件里出现；
- 加一个字段要改多处，漏一处就门禁误报或静默失效；
- 手抄的那份与源码不一致时，没有任何机制会立刻发现。

## 本仓已收敛的实例

| 手抄过的内容 | 收敛方式 | 位置 |
| --- | --- | --- |
| 规模表字段正则（build-ir / ir-validate / parity-check 各一份） | 共享解析器 | `tools/scales-parse.mjs` |
| 构建参数（package.json 的 build:print 与门禁自举） | 单一脚本 | `build/build-print-all.mjs` |
| 主题包字段契约 | 从源码派生的校验器 | `tools/theme-schema.mjs` / `tools/theme-validate.mjs` |

## 配套纪律

1. **派生型白名单为空时必须判红**，不能静默跳过。
   反例：判据写成 `if (allowed.length > 0 && !allowed.includes(v))` ⇒
   白名单一旦派生失败，整条检查静默失效。
   正解：白名单为空 ⇒ 报「无法派生，检查已失效」并判红。
2. **派生器自身要有常驻断言**：白名单非空且与源码一致。
3. **参数取值域要单独覆盖**：参数名合法只是半个盲区；
   正整数 / 枚举成员 / 座位范围 / 格号范围 / 引用存在性要各自覆盖。
4. **手抄的东西要有反例记录**：写下「漏改哪一处会怎样」，让下一个改动者能自查。

## 为什么门禁脚本不经 shell

Windows 上 `npm.cmd` 无法用 `shell: false` 直接执行（EINVAL）；若为了调用 npm 而写 `shell: true`，
就会触发门禁纪律 A4（退出码语义不可信）。
⇒ 解法：把构建逻辑放进**纯 node 脚本**（`build/build-print-all.mjs` 用 esbuild 的 JS API 自编译），
门禁与 npm 都指向它 ⇒ 既不经 shell，又只有一处参数。
