# 负样本自证范式（违例必红、恢复必绿）

规格 §9.3 要求：每道门禁都要有常驻负样本 —— 制造缺陷 ⇒ 门禁必红；恢复 ⇒ 门禁必绿。
本文件是可复制的操作范式（B13 实证：`tests/gates/duel-negative.test.ts`）。

## 核心难点：不能在共享工作树上制造缺陷

直接在共享工作树改引擎源码跑并行测试 ⇒ 并行的 `node --test`（门 2）读到坏代码 ⇒ 门 2 假红，
无法区分「真因」与「污染」。⇒ 必须用隔离临时目录改副本。

## 四要素

1. 副本内容：只复制被测对象（引擎 / 主题 / 前端 / 被测入口），不复制整个仓库。
2. 副本 cwd 指向副本：被测入口的相对 import 与资源读取都必须落在副本内，否则「改副本」形同虚设。
3. 依赖解析：副本没有 node_modules 时，用 junction（Windows）/ symlink 链接只读依赖；
   或让脚本留在仓库、用环境变量把根目录指向副本（如 `CM_BUILD_ROOT`、`CM_REPO_ROOT`）。
4. 正样本对照：同一副本未破坏时必须绿 ⇒ 证明「红」来自缺陷，而不是副本环境本身跑不起来。

## 用例矩阵（B13 的 5 用例）

| 用例 | 破坏点 | 期望 | 证明的事 |
| --- | --- | --- | --- |
| 负样本 A | 引擎丢掉对峙消费点 | 门 9 必红 | 模拟器可达性断言真的在把关 |
| 负样本 B | 同上 + 副本自建 bundle（副本起点无 dist） | 门 10 必红 | E2E 不依赖仓库已构建产物 |
| 负样本 C | E2E 的断言被破坏 | 门 10 必红 | 断言机制本身有效（不是环境问题） |
| 正样本 A | 不破坏 | 门 9 必绿 | 副本环境可用 |
| 正样本 B | 不破坏 + 自建 bundle | 门 10 必绿 | 副本 bundle 可用 |

## 自检纪律

- 必须带正样本：没有正样本的负样本无法排除「环境本来就坏」。
- 必须 finally 清理临时目录（`rmSync(dir, { recursive: true, force: true })`）。
- 验收口径：跑完 `git status` 前后完全一致 ⇒ 证明共享工作树全程只读。
- 副本套副本必须排除自身：负样本脚本复制的是 `process.cwd()` ⇒ 若在副本里运行它，
  它会再复制副本自己 ⇒ 无限套娃。⇒ 副本清单里排除该脚本（仓库侧的保障不受影响）。
- **判据（更严，B17 教训）：负样本若对仓库有任何写入，就不是负样本**。
  「集中在同一个测试文件里改→跑→恢复」只解决了**负样本之间**的并发冲突，
  **没解决与其它测试文件的冲突** —— 门禁② 跨文件并发跑，并行读的测试会读到
  「破坏窗口内的中间态」⇒ 门禁瞬时假红（实测：单跑全绿、门禁红）。
  ⇒ 一律用 `tools/repo-copy.mjs` 的 `makeIsolatedRepo()` 建隔离副本，**共享工作树全程只读**。

## 常见坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| 副本缺 node_modules | import playwright 解析失败 | junction 链接；或 `createRequire(resolve(ROOT,package.json))` 从仓库解析 |
| 脚本用 process.cwd() 定位根 | 副本里指向错误目录 | 用环境变量覆盖根目录（CM_BUILD_ROOT） |
| 产物依赖仓库 | 副本测的还是仓库代码 | 副本自建 bundle，断言「副本起点无 dist」 |
| 负样本污染并行测试 | 门 2 假红 | 只改副本，共享树只读 |
| 脚本被 A4 纪律门抓 | 门 2 红在 discipline.test.ts | 门禁脚本不得 shell: true、不得接管道 |
