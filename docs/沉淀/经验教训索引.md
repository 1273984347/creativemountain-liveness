# 经验教训索引（B8–B13 实证 → 跨项目通用结论）

本索引只列**已在本仓实证过、且已通用化**的结论。每条给出：现象 → 根因 → 通用化 → 落地位置。
原始执行记录在 `docs/批次/`（过程与数据），本索引（方法与规则）。

## 一、机制可达性

| # | 现象 | 根因 | 通用化 | 落地 |
| --- | --- | --- | --- | --- |
| E1 | 7 个身份被动的 op 只在主题包里出现，引擎零消费点 ⇒ 触发次数恒为 0 | 机制注册了、文案写了，但没有消费点 | 「只写不读」= 死机制。必须 grep 到消费点，并断言「真实对局中触发过」；只测「执行算子后状态变了」不够 | B12 记录；`engine/core/abilities.ts` |
| E2 | 移动到峰顶只置 `pendingCert`，没调用 `enterPendingCertification` ⇒ 认证流程永不启动，而单测全绿 | 单测只测了流程函数本身，没测入口是否被接上 | 单测直接调流程函数会漏掉「入口是否被调用」。必须区分单元契约测试与集成测试 | B13 记录 |
| E3 | `extra_vote` 补上读取逻辑后仍无效 | 山议计票硬编码了仲裁者权重，顶替了机制 | 补读取逻辑时必须一并改掉「硬编码顶替路径」，并同时断言「机制等价」与「机制可推广」 | B10 记录 |
| E108 | **「判定器存在」≠「判定被调用」**：`goals/registry.ts` 的 8 个 kind 判定器齐备，`pass_gates` 的计数器只要有人写就能达成 ⇒ 但该文件在**生产代码里零 import**（只有测试引用）⇒ 即便补上写入方，目标仍**没有任何可观测后果**（「达成即发印记」的写方同样不存在）⇒ 缺陷登记里「不可达」的**归因只覆盖了写入方一环** | 把「机制可不可达」归因到**单个环节**（此处：计数器无写入方），没顺着链路往下查**判定调用点**与**奖励发放点** | 登记机制不可达时必须**顺着整条链逐环核实**：数据产生 → 判定 → 奖励生效；**每环都要有独立的读方与写方**，缺一环即不可达 ⇒ 修复也须**逐环补齐**，只补一环等于没修 | B60 记录；`engine/goals/settle.ts` |
| E111 | **「达成次数为 0」有两种根因，必须用「计数器的实际值分布」区分**：只看「目标达成次数」会把「计数写了但**未达阈值**」误判成「计数器根本没写（机制缺失）」⇒ 于是去补计数器 / 改机制 ⇒ **改错了地方** | 只报「达成次数」这一个数 | 报达成次数时**同时报计数器的实际值**（最大值/均值）⇒ **最大值 = 0** ⇒ 机制缺失（事件从不发生）；**最大值 > 0 而未达阈值** ⇒ 标定/策略问题；并把该分布做成**常驻报告章节** ⇒ 根因分类从此有据可依 | B61 记录；`docs/balance-report.md` |
| E112 | **补计数器前必须先查「事件是否存在」**：某目标所依赖的机制**根本没实现**（op 存在但**零使用者**、动作入口缺失）⇒ 补上计数器只会造出「**永远为 0 的假可达**」——读起来像「已修」，实际仍不可达 | 「规格列了目标 ⇒ 事件就存在」；只查计数器有没有写 | 补计数前**逐环核实**：机制实现 → 事件发生 → 计数写入 → 判定调用 → 奖励生效；**任一环缺失** ⇒ 该目标**如实登记为机制缺失**，不补假计数器（宁可留缺口，不留假绿） | B61 记录；`engine/goals/settle.ts` |
| E113 | **审阅意见 ≠ 裁决：既有裁定优先**；且**测试名承诺 ≠ 断言体**：盲审建议「在判定入口加引擎级幂等守卫」，但既有裁定明写「去重由粗筛承担」且门禁层**登记**了「UI 比引擎严」的口径 ⇒ 照改会**推翻既有裁定并让门禁变红** ⇒ 改为在**不动既有口径**的前提下达成同样目的（计数侧幂等）；另一条：用例名写着「复议推翻 ⇒ −1」而断言体只测 +1 ⇒ **名实不符掩盖了零覆盖**（mutant 撤掉 −1 仍全绿） | 把审阅意见直接当裁决；用例名写得比断言体更强 | 收到审阅意见先查**既有裁定与门禁登记**是否依赖被建议改动的行为 ⇒ 若依赖 ⇒ 不直接照改，改在**不动口径**的前提下达成目的；⇒ **用例名承诺的每个分支都要有对应断言**（否则名字成了遮羞布） | B61 记录；`tests/engine/goals.test.ts` |
| E116 | **「零调用方」类缺陷的归因要顺着「跳过分支」查，且确定性重放里数字差异就是行为差异**：G-g 登记的是「投票写进一个没人关闭的窗口」，实测发现更严重 —— 轮末结算**主动跳过**已申请复议的座位 ⇒ 生产路径下待认证者**永不被结算**（卡在峰顶）⇒ **调用方缺失只是表层**；同时把平衡报告的 22303→22300 冠以「采样级差异」⇒ **误判**（模拟是固定 seed 的**确定性重放**，逐字可比 ⇒ 差异 100% 来自行为改变） | 只 grep「有没有调用方」就下结论；把**确定性**模拟的读数变化当成噪声 | ① 「无人调用」类缺陷必须**顺着调用链往下看「谁在跳过它」** —— 跳过分支往往才是真正的**主体不可达**（不调 ≠ 不需要，可能正是「等它来管」而它没人来）⇒ 归因要覆盖到**主体是否被结算**；② 报告读数变化**先问「确定性还是采样」**：确定性 ⇒ 逐字可比 ⇒ 差异**必须**归因到行为，**不许**冠以「采样级差异」；③ 行为改变用 **A/B 对照**坐实（同一局面在基线代码与改动代码各跑一次，比**可观测状态**而非读数） | B63 记录；`engine/core/certification.ts` |
| E118 | **「字段没有语义」≠「字段免费」；且确定性回归锁的阈值必须按「跨样本最大」定**：① 给「出牌费用」立规则时发现卡牌 `cost` **在规格里根本没有规则语义**（§3.1「行事」未写支付、§8 支出表未列「出牌」）——真读起来像「免费」，但 §8 **逐条列了所有有代价的动作** ⇒ 缺的是**一条规则**，不是「免费这条规则」；② 付费落地后**门 ⑫ 变红**（8 人局极差 5.9 → 13.4pp），若只把阈值调大就完事 = **用口径掩盖机制性偏差**；③ 阈值若按**单个切片**读数 × 余量来定，而该切片恰落在分布**下沿** ⇒ 阈值偏低 ⇒ 门禁**随机红**（违反「零 flake」前提） | 把「规格没写」读成「规格说它免费」；用口径改动掩盖机制性偏差；用单切片估噪声 | ① 判定前先看**同一份权威文档里其它同类条目怎么写的**（缺条目 ⇒ 缺规则，不是缺许可）；② 规则改动的连带影响要**顺着下游门禁查** ⇒ 先**隔离变量**（哪个改动贡献了多少）、确认偏差是**噪声还是机制性**，再决定改机制还是改口径；③ 确定性回归锁的阈值 = **跨样本中位数**作基线 + **跨样本最大** + 余量 ⇒ 对任意切片零 flake | B65 记录；`engine/core/balance.ts` |
| E119 | **「规格早就对、只差实现」与「规格没写、须立规则」是两类缺陷**；且**类型标签不是语义**、**变异自证的前提自查不得调用被测函数**：① 补「待认证锁定」时发现规格 §5.1 与 §13.4 裁定表**早已写明**「不能使用移动类卡牌或位移能力」⇒ 只差引擎实现（与「出牌费用」那类**规格没写、须先立规则**的缺陷性质相反）⇒ **先看规格有没有写**，能省掉一整轮评审；② 判「一张牌含不含位移」时，**只看 `card.type === 'motion'` 会漏** —— 主题包里有一张 **utility 类型**的位移牌 ⇒ 必须按 **op 语义**判；③ 写变异自证时用**被测函数**去找测试用的牌 ⇒ 「判据退化成只看 type」的 mutant 会让**前提先失败** ⇒ 自证红在「前提自查」而非专属断言上 ⇒ **判据失准**（证明的是「前提会红」，不是「该层有锁」） | 把两类缺陷当同一类处理（都去改规格）；把卡的 type 标签当成语义；用被测函数构造测试前提 | ① 先查规格与裁定表：**已有裁定 ⇒ 只补实现**（规格零改动）；**没有 ⇒ 先立规则再实现**；② 「某类卡/效果」的判据按 **op 语义**而非标签判（与「按 op 排 AI 出牌强度」同款思路）；③ 变异自证的**前提自查不得调用被测函数** ⇒ 前提改为直接查底层数据，否则 mutant 的判红位置会失准 | B66 记录；`engine/core/targeting.ts` |
| E117 | **同一条口径在仓内有 N 份复制时，先收敛唯一出处再展示**：做「UI 显示复议窗口状态（谁还没投）」时发现「独立第三方 = 存活 − 判定人 − 待认证者」这条口径在仓内已有**两份复制**（引擎 `resolveAppeals` 内联一份 + 探针 `appealTally` 自抄一份，注释还自称「复用公开口径」）⇒ 若直接在 UI 里再写一份，就是**第三份** ⇒ 三处各自演化 ⇒ **显示的「未投人数」与实际裁定口径不一致** ⇒ 玩家看到假数字 | 把「展示信息」当成纯 UI 活 ⇒ 直接在渲染层再写一遍判据；抄一份口径时不查仓内是否已有出处 | ① **先抽唯一出处**（口径属裁定规则 ⇒ 放引擎并导出），让**所有消费方取用**（UI / 探针 / 裁定本身），调用方**不允许自己算**；② 配套一条**结构类断言**（源码形状：不得手写该口径）⇒ 第二事实源回流即红（只有结构断言能挡）；③ 展示口径要用**裁定面**而非**接受面**（本仓二者不等价：同场另一名待认证者在裁定面上要投票） | B64 记录；`engine/core/certification.ts` |

| E114 | **「沿用旧诊断」不等于「已知根因」**：把一处偶发失败归因为「某模块的跨秒时序」，那是从旧批次**抄来**的；本批独立复现 **50+ 次（串行 + 并发）全部落空** ⇒ 该归因**不成立** ⇒ 继续当事实传下去，下一批会照着**错误方向**去查、甚至改生产代码 | 登记缺陷时把「结论」直接当「证据」；只引用来源而不复现 | 登记缺陷时「根因」那一栏**必须有本批的复现证据**（复现次数 + 是否复现 + 已排除什么）⇒ 否则只能写「**未确定**」；⇒ 诊断**未复现**时优先交付「**可诊断化**」（失败时打印差异偏移与区段）+「**确定性的核心命题用例**」，而不是凭猜测改生产代码 | B62 记录；`tests/gates/pdf-normalize.test.ts` |

| # | 现象 | 根因 | 通用化 | 落地 |
| --- | --- | --- | --- | --- |
| E7 | 4 人局全员并列最高票时一次放逐多人，存活数打到下限以下（24000 局出现 1 次） | 下限判据按「逐个提名者」判断 | 数量上限/下限规则若一次可处理多个对象，必须用**累计口径**；且这类低频边界必须靠单测钉住，不能指望模拟撞出来 | B10 记录 |

| E9 | 参数扫描副本与生产模拟器读数差 9pp，差点得出反向结论 | 扫描代码是另写的一份实现，漏了一次状态赋值 | 扫描/实验代码必须**复用生产入口**（加临时开关覆盖），不要复制一份实现；临时开关收官前删干净 | B11 记录 |
| E10 | 造物牌 cardId 与普通牌同名，看着像 id 冲突 | 造物牌本就**必须**引用普通牌 id，校验器强制这条 | 看起来该修的重复值/重复 id，先读校验器的判据 —— 它往往编码着设计意图 | B12 记录 |
| E11 | 对峙/新机制引入后，同一函数里的早 return 分支让后续逻辑永不执行 | 多职责共用一个 switch，分支提前 return | 同一函数承担多个职责时，要么分离成两段，要么所有分支走同一条出口（break + 统一收尾） | B13 记录 |
| E12 | 自动落败分支用「未选牌 == undefined」判断「无牌可选」 | 「未完成 / 不存在 / 为空」三个语义复用了同一个 undefined | 状态判据要用各自的语义字段，不能都落到 undefined 上 | B13 记录 |
| E110 | **派生数据放进 `flags` 会打破「标记应清空」类断言**：把身份目标派生到 `player.flags.goal` 后，既有的「换主题 ⇒ 标记应清空」深度相等断言立刻红 | `flags` 的语义是「玩家标记（`set_flag`/`clear_flag`）」，但**新一局派生的数据**（身份被动规格 `passive`、身份目标 `goal`）也落在这里 ⇒ 「临时标记」与「本局派生量」混在一处 | 新增「每局派生」的运行时数据时优先找**语义匹配的既有字段**；实在只能落 `flags`，则**同步精确化**既有断言（排除派生量，并**额外断言它来自新一局**）⇒ 与既有先例（`flags.passive`）保持同款处理，而不是笼统地改断言 | B60 记录；`tests/engine/themes-play.test.ts`|

## 四、门禁与协作

| # | 现象 | 根因 | 通用化 | 落地 |
| --- | --- | --- | --- | --- |
| E13 | 在共享工作树改引擎源码跑负样本，门的第 2 门假红 | 并行的 node --test 读到坏代码 | 负样本必须在**隔离临时目录改副本**；验收口径 = 跑完 git status 前后完全一致 | 本目录「负样本自证范式」 |
| E14 | 干净 clone 后门禁必红（门 6/7 依赖不在版本库的 print 产物） | 产物是生成物（.gitignore），门禁却假定它们存在 | 门禁要**产物自举**：缺失才生成，且生成命令不经 shell（纪律 A4） | `tools/gate.mjs` 的 `ensurePrintArtifacts` |
| E15 | 副本里跑负样本脚本会无限套娃 | 负样本脚本复制的是 process.cwd()（副本自己） | 副本清单必须排除负样本脚本自身 | `docs/沉淀/clean-room-gate-check.mjs` |
| E16 | 门禁脚本为调用 npm 写 shell: true ⇒ 被纪律门 A4 判红 | Windows 上 npm.cmd 无法无 shell 执行 | 把构建逻辑放进纯 node 脚本，门禁与 npm 都指向它 ⇒ 不经 shell，且参数只有一处 | `build/build-print-all.mjs` |
