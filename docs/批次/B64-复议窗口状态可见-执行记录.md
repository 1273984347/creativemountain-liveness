- **做**：① 认证面板在复议窗口打开时显示**第三方人数 / 已投 / 未投（点名谁）**与**窗口何时关**；② 把「独立第三方集合」抽成引擎的**单一事实源**（`appealThirdParties`）⇒ UI、探针、裁定三处同源；③ 补常驻断言 + **3 条专属变异自证**。
- **不做**：改**引擎语义**（复议怎么裁、窗口何时关 —— B63 已裁定，本批只让玩家**看得见**）；改规格；扩复议票以外的面板信息。

## 2. 取证：发现口径有**两份复制**

| 步骤 | 做法 | 结果 |
| --- | --- | --- |
| ① 读 UI 面板 | `web/ui/cert.ts` | 复议窗口打开时**只挂两个投票按钮** ⇒ 玩家看不到「还差几票」「谁还没投」「窗口什么时候没」⇒ **B63 遗留 T2 的原文** |
| ② 找权威口径 | `engine/core/certification.ts` 的 `resolveAppeals` | 「独立第三方 = 存活 − 判定人 − 待认证者」——**但它是内联的**（未导出） |
| ③ 查仓内其它副本 | `grep "独立第三方"` | ⚠️ **`tools/laya-probe/state-text.mjs` 的 `appealTally` 把这条口径抄了第二份**（注释自称「复用公开口径」，实为**重写**） |
| ④ 评估风险 | —— | 两份各自演化 ⇒ UI/探针显示的「未投人数」可能与**实际裁定口径**不一致 ⇒ 玩家看到假数字 ⇒ **必须收敛到唯一出处** |

> ⚠️ **本批最重要的产出不是那行文案，而是「同一条口径在仓内有 N 份复制」这个结构问题**：T2 若直接在 UI 里再写一份口径，就是**第三份** ⇒ 假数字从「可能」变成「必然」。

## 3. 关键裁定

| # | 争议点 | 裁定 | 理由 |
|---|---|---|---|
| 1 | 「谁还没投」按哪套人算？ | 取**裁定面**的第三方集合（`appealThirdParties`） | 与 `resolveAppeals` 同源 ⇒ 显示与实际裁定**不会漂移**。⚠️ 注意**接受面 ≠ 裁定面**：`certifyAppealVote` 只排除申请人与判定人，而裁定面把「存活 − 判定人 − 待认证者」全算第三方 ⇒ **同场另一名待认证者**在裁定面上要投票（规格：票只发给非当事人）⇒ UI 展示必须用**裁定面**那套 |
| 2 | 口径放哪？ | 抽成**引擎导出函数** `appealThirdParties`（单一事实源） | 口径属**裁定规则** ⇒ 属引擎；UI 与探针都取用它 ⇒ 调用方**不允许自己算** |
| 3 | `resolveAppeals` 要不要改？ | **要** —— 改为调用该事实源 | 否则引擎内仍留一份内联复制 ⇒ 事实源不唯一（等于没抽） |
| 4 | UI 文案放哪？ | 抽成**纯函数** `appealWindowStatus`（导出） | 测试可**无 DOM** 断言（沿 `certClickableActions` 的先例）⇒ 不必渲染就能钉住文案 |
| 5 | 文案算不算「可点性判据」？ | **不算** —— 只读展示 | 可点性**唯一来源**仍是 `uiAllows`（发现 A 的承诺不能破）⇒ 本块只加信息、不改按钮显隐 |
| 6 | 第三方不足 2 人时怎么说？ | 说「**掷 6 面骰**」，**不说「多数决」** | 掷骰路径下说「多数决」会误导玩家以为要凑票 ⇒ 文案必须与**实际裁定分支**一致 |

## 6. 复盘与经验沉淀

- **口径有 N 份复制时，先收敛再展示**：本批若直接写 UI 文案，就会造出**第三份**「独立第三方」口径 ⇒ 展示数字与裁定数字可能不一致 ⇒ 玩家看到假信息。⇒ **先抽唯一出处，再让所有消费方取用**。
- **「展示什么」也要按**裁定面**而非接受面**：接受面（谁能投票）与裁定面（谁算第三方）在本仓**本来就不相等**（同场另一名待认证者）⇒ 展示若用接受面 ⇒ 玩家会去等一个不该等的人投。
- **变异自证要覆盖「结构」**：本批的 T2-2 钉的是**源码形状**（不得手写口径）⇒ 只有结构类断言能挡住第二事实源回流。
