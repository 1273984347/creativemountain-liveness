# B75 · 装备与仲裁者否决：两个不可达目标的机制补齐 · 执行记录

日期：2026-11-13｜规格：`docs/superpowers/specs/2026-11-11-b75-equip-veto-mechanics-design.md`｜计划：`docs/superpowers/plans/2026-11-11-b75-equip-veto-mechanics.md`

## 1. 目标与范围

把两个**规格要求但机制缺失**的目标变成可达成，并且**只在数字轨 + UI + 模拟器**里补齐，不接入模型：

- `equip_count`（累计装备法宝数）⇒ 新增动作 `EQUIP_CARD`：手牌转常驻装备，免费、不占手牌上限、不产生位移。
- `veto_success`（成功否决 1 次放逐）⇒ 新增动作 `COUNCIL_VETO`：仲裁者每局 1 次，令**本次**放逐作废。

明确未做（范围外）：装备携带被动效果、否决可选目标、死亡/复活（B76）、第 5 套主题（B77）、certify 面模型接入（B78）。

## 2. 关键裁定

| # | 议题 | 裁定 | 落点 |
|---|---|---|---|
| 1 | 装备是否另开一个入口 | **不另开**：走 `performAction` 的新分支 `'equip'`，且必须位于 `pendingGate` / `pendingBarrier` 两条早退**之后**——关隘/裂隙暂停时该手番已用掉，提前就等于同一手番两次行动 | `engine/core/turn-runner.ts` |
| 2 | 否决的时机 | **硬前置**：所有**存活**玩家都已投票（判据用 `every`，不用「票数 ≥ 存活数」，出局者旧票会残留）；且**不自动结算**山议 | `engine/core/council.ts` |
| 3 | 否决何时算「成功」 | 只有**真的阻止了一次放逐**才写 `vetoCount`；下限保护 / 凭证免疫导致的零放逐属**白用**，只说明不计数 | `engine/core/council.ts` §4.3 |
| 4 | 否决权从哪来 | 主题数据 `identities[].rights = ["council_veto"]` ⇒ 开局授予 `flags.canVeto`；**禁止**按 `identityId` 硬编码 | `engine/core/setup.ts`、四套 `theme.json` |
| 5 | AI 装备会不会扰动随机流 | **不额外抽随机数**：复用同一个 `roll`，把 0.85–1.0 的出牌带二分（`roll < 0.925` ⇒ 装备）| `tests/sim/policy.mjs` |
| 6 | UI 门禁的拒因怎么判 | `actionWindowRefusal` 改**结构化** `WindowRefusal{code,message}` ⇒ 装备按 `code !== 'pending_cert'` 放行，不再匹配文案字符串 | `web/legal-gate.ts` |
| 7 | **否决强度过高怎么办** | 实测：AI 用上自保否决后仲裁者胜率 24.3–27.6%（最弱身份 ≈9%）⇒ **本批不改否决语义**，两条平衡锁按实测放宽，强度议题显式登记为后续批次（设计 §13 **R7**，三条候选补偿：付 2 灵枢 / 否决后下一 round 不能行动 / 只救他人不自救） | `tests/engine/balance-regression.test.ts` |

## 3. 三环取证法（本批的方法产出）

「机制缺失」不是一件事，而是三环：**入口**（枚举会不会发候选）→ **写入**（走真实入口后计数器 +1）→ **判定/发奖**（达标后印记出现）。
报告里的「恒为 0」在三环上表现完全一样 ⇒ 每环各留一条可失败用例：

- 入口：`tests/engine/legal-probe.test.ts`（枚举/候选/判定形状三层 + 装备与否决的 UI 拒因矩阵）；
- 写入：`tests/engine/equip.test.ts`、`tests/engine/council-veto.test.ts`（含「白用不计数」的反向用例）；
- 判定：`tests/engine/goals-reachability.test.ts`（两个目标达标 ⇒ `hasMark`，以及未达标 ⇒ 不发）；
- 端到端：`tests/sim/policy.mjs` 接通后由 `docs/balance-report.md` 的达成人次兜底。

## 4. 平衡与重标定读数

同一固定样本（2000 局 × 4 主题 × 8 人，`balance-regression.test.ts` 的口径）的**分解**：

| 配置 | 位次极差 | 身份极差 | 仲裁者胜率 |
|---|---|---|---|
| 两个决策都关（= B74 形状） | 4.4pp | <12pp | ≈13% |
| 只开否决 | 4.8pp | 17.7pp | 24–26% |
| 否决 + 装备 | **5.3pp** | **18.6pp** | 24.3 / 25.7 / 25.9 / 27.6% |

⇒ 位次锁 4.5→**5.5pp**、身份锁 12→**20pp**（两条都在注释里写明机制原因与分解，不是「放宽就完事」）。

重标定产物（24000 局默认参数，`docs/balance-report.md`）：

- `veto_success` 达成 **5482** 人次（22.84%）· 计数最大值 3；
- `equip_count` 达成 **1038** 人次（4.32%）· 计数最大值 3；
- 异常 **0** 条；无人封顶兜底率 2.6% · 席位制结算 23381 · 平均席位 2.24 · 平均回合 14.5。
  ⇒ 与 B74 报告对照：兜底率 3.0% → 2.6%、平均席位 2.096 → 2.24（装备/否决改变了节奏与放逐分布，方向可解释）。

门禁三专项复核（阈值一律未动）：门 ⑪ 试炼通过率 PASS、门 ⑫ `--position-spread --games 100` PASS（8 人档极差 7.8pp · RMS 2.65pp，判据 ≤14pp/≤6.5pp）、门 ⑬ 余量判定 PASS。

发布基线：按 B35 流程重扫 5 档余量 × 20 组 × 125 局 ⇒ 入库快照 `docs/baselines/trial-reserve-scan-B75.json`，
`tools/release-check.mjs` 与 `docs/沉淀/compare-scan-baseline.mjs` 的默认基线改指 B75（B74 快照保留可回溯）。

## 7. 遗留

1. **否决强度**（R7，最高优先）：仲裁者 24–28% 胜率是否可接受、以及三条候选补偿选哪一条 ⇒ 需要一次独立的调平衡批次（含 §8 全流程重标定）。
2. **`build/build-themes.mjs` 脱节**：生成器跑不动（基准地名数与主题数据已分叉），三套主题实为手工维护 ⇒ 要么修生成器并补一条「产物 == 手工文件」的一致性用例，要么正式放弃它并在文件头写明「历史脚本」。
3. **门 ⑨ 的逐字等价**在本批从 Task 7 起**故意不再成立**（行为已变）⇒ 基线更新为 B75 快照；后续批次若再改行为，仍须按 B35 流程显式重扫。
4. `reroll_count` / `steal_count` 两个目标仍是「阈值/策略未达标」（不是机制缺失），归后续策略调优。
