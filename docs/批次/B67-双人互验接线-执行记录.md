## 3. 关键裁定（6 项）

| # | 争议点 | 裁定 | 理由 |
| --- | --- | --- | --- |
| 1 | 互签怎么触发？ | **待认证者自己的一个认证动作**（与签印 / 质疑 / 弃权并列，走 Action 契约） | 规格 §5.5「两人**互相出题、互相签印**」⇒ 玩家须**参与**；引擎自动互签则玩家没参与，与「互相出题」的戏剧性相悖 |
| 2 | 能不能复用 `CERTIFY_SIGN`？ | **不能**，新增 `CERTIFY_MUTUAL_SIGN` | `CERTIFY_SIGN` 是**认证人**（存活、非待认证者）签**待认证者**（引擎 `isCertifier` 守卫）；互签是**待认证者**签**待认证者** ⇒ 两者语义相反，复用会把「认证人签待认证者」与「互签」混成一条 |
| 3 | 「本轮一次机会」对互签成立吗？ | **成立**（互签者记入 `signed`） | 否则一个座位可给同伴**无限刷签印** ⇒ 绕过「每人每轮一次选择」 |
| 4 | 用哪个字段记互签？ | **复用既有 `signed`**，**不新增字段** | 规格 §6.2 的 State 契约**已冻结**（B1 起「不再变更」）⇒ 新增 `mutualSigned` 要动契约；而 `signed` 正是「本轮已用掉认证机会」的既有载体（`hasUsedCertificationTurn` 就查它）⇒ **语义自洽**，且互签者必是待认证者、认证人必不是 ⇒ 两类记录**不互相污染** |
| 5 | 互签与复议冲突吗？ | **不冲突**（两个独立入口） | 申请复议**不**占用互签（复议不记 `signed`）⇒ 玩家申请复议后仍可与同伴互签 ⇒ 三层候选条件必须**同款**（否则漂移守卫必红） |
| 6 | 门槛与席位语义要改吗？ | **不改** | 规格 §5.2 步骤 0 已写「双人同时待认证 ⇒ `base = 1`，跳过 min、不走印记减半」；B11 裁定「双方各得 1 席、不结束本局」⇒ **实现即可** |

## 7. 复盘与经验沉淀

- **「只有引擎函数」与「机制已接线」之间隔着四层**：Action 契约 → 枚举层 → 面板/UI → 模拟器。⇒ 判「机制可达」要**逐层数**，只看引擎有函数会误判（**这是 E108「判定器存在 ≠ 判定被调用」的同族，但更靠前**）。
- **三层候选条件必须同款**：引擎粗筛 / UI 候选 / 面板动作三处各写一份条件 ⇒ 任何一处不同款，漂移守卫立刻判红（本次实测抓到 3 处不一致）⇒ **让守卫当「三处口径」的牙齿**，比人工核对可靠。
- **穷尽 switch 是免费的检查器**：新增 Action 类型后 `tsc` 立刻指出三处缺分支（`action-key` / `probe` / `legal-gate`）⇒ 不用人工搜「哪里 switch 过 Action」。
- 已写入 `docs/沉淀/经验教训索引.md` **E120**（机制可达要逐层数；三层候选条件须同款；穷尽 switch 是免费检查器）；Agent Memory 同批沉淀 1 条。
