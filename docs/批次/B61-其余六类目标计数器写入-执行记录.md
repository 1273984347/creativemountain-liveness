## 1. 目标与范围

- **做**：为 `draw_count` / `reroll_count` / `steal_count` / `successful_challenge` 四类目标补上**计数器写入点**（含 `immediate` 判定点接线），并把「达成次数为 0」的**根因逐类查清**。
- **不做（授权内但机制层无事件可计 ⇒ 如实登记，不补假计数器）**：
  - `equip_count`（`equipsTotal`）—— 规格 §4.1 给匠师的目标是「累计装备 3 件法宝」，但**没有任何机制产生「装备」**：`equip_card` 在四套主题包**零使用者**、`performAbility` 无该分支、规格无「装备」动作入口 ⇒ **事件永不发生** ⇒ 补计数器只会造出一个「永远为 0 的假可达」。
  - `veto_success`（`vetoCount`）—— 依赖「仲裁者否决放逐」机制：**引擎未实现**（`engine/core/council.ts` 只有注释）；且规格**内部不一致**（§5.6 line 461 有「仲裁者否决」，而 §4.1 权威被动表里仲裁者只剩「投 2 票」）⇒ 属**机制缺失 + 规格待裁定**。
- **不改规格**：本批只补实现，规格零改动（doc-sync 10 项检查仍全绿）。

## 3. 关键裁定（8 项）

| # | 争议点 | 裁定 | 理由 |
|---|---|---|---|
| 1 | 抽牌计入哪些来源？ | **所有「玩家获得的牌」都计；开局发牌不计入** | 开局发牌是**初始配置**（起手）而非「抽」；含它会让 count=12 的目标在开局就达成一半 ⇒ 口径失真。⚠️ 抽牌有**两个独立实现**（`hand.ts` 的 `drawCards` 与 `registry.ts` 的 `draw_cards` op，失败语义不同：前者静默跳过、后者 `ok=false`）⇒ **两处都要计数**，实到张数为准 |
| 2 | 抽牌计给谁？ | **获得牌的人** | 计数器是「玩家的累计」⇒ 归属获得方 |
| 3 | 「改判」= `reroll` 还是 `modify_judgement`？ | **`modify_judgement`** | 规格 §6.4 表的达成条件用词是「累计**改判**次数」，而 `reroll` 的语义是「重掷骰子」（参数盘点 G5 已明确二者不同）⇒ **以达成条件用词为准**；kind 名 `reroll_count` 与语义不一致，**属命名遗留**（登记 T4） |
| 4 | 改判计给谁？ | **被改判者**（`modify_judgement` 的 target 座位） | 规格「织梦者：改写**自己**的险径判定」⇒ 织梦者的改判（target=self）计自己 ✔ |
| 5 | 偷取计给谁？ | **偷取者**（`performAbility` 的 `transfer_resource` 分支的 actor 座位） | ⚠️ 计价点**不是 op 本身**：`transfer_resource` 的语义是「actor 转给 target」，窃火者靠**交换 actor/target** 实现「目标 −1、自己 +1」（`abilities.ts`）⇒ 只有**被动发动**才是「偷取」⇒ 计数点必须在被动侧 |
| 6 | 「成功质疑」= 答对还是答错？ | **答错**（`certifyAnswer` 的 `passed=false`） | 规格 §5.3.2 line 419：「质疑**成功**（答对 ≤ 1）」⇒ 质疑成立 = 待认证者答错 ⇒ 计数归属**发起质疑者** |
| 7 | 「未被复议推翻」怎么保证？ | 判不通过时 **+1**；复议**推翻**（`applyAppealOutcome` 的 success）时 **−1**（可逆） | 规格要求「且该次未被复议推翻」⇒ 计数须随复议回退 ⇒ 共享 helper 支持负 delta |
| 8 | `immediate` 判定点在哪？ | **质疑判不通过之后**（`certifyAnswer` 内） | 规格 §6.4：「即时结算（否决生效时 / 质疑成功时）」⇒ 事件发生处即判定点；⚠️ 复议回退后计数可能低于阈值，但**印记不叠加**⇒ 已发印记保留（如实登记 T3） |
| 9 | **重复判定**要不要在引擎层拒绝？（盲审必修项·二） | **不收紧引擎接受面**，改在**计数侧**做幂等 + 改判回退 | 既有裁定「`certifyAnswer` 无重复判定守卫 ⇒ **去重由粗筛承担**」（`engine/core/legal.ts:142-143`），且门禁层**登记**了「重复判定 = 引擎接受、UI 不给点」这条「UI 比引擎严」口径（`tests/engine/legal-probe.test.ts` 的 `registeredUiStricter`）⇒ **引擎加守卫会推翻既有裁定并让那条门禁变红** ⇒ 不擅自改口径。⇒ 改为：① 计数**幂等**（同一 actor 只计一次）；② 改判为通过时**回退 −1**（该次质疑不再成立）⇒ 探针/外部路径也不虚高 |

## 6. 复盘与经验沉淀

- **「达成次数为 0」有两种根因，必须用「计数实际值分布」区分**：只看达成次数，会把「阈值偏难」当成「机制缺失」⇒ 就会错误地补计数器 / 改机制。本批的 `reroll_count`（最大值 2、阈值 3）与 `steal_count`（最大值 1、阈值 5）都是**计数在写、只是没达标**；而 `equip_count`/`veto_success` 的最大值 **0** 才是真的机制缺失。⇒ 已把「计数实际值分布」做成 sim 的**常驻报告章节**（跨项目通用纪律）。
- **补计数器前必须先查「事件是否存在」**：六类里有两类的机制**根本没实现**（装备动作、仲裁者否决）⇒ 补计数器只会造出「永远为 0 的**假可达**」⇒ 宁可如实登记，也不补假计数器。
- **口径要逐条现查，不能照抄计数器名**：`transfer_resource` 的语义是「actor 转给 target」，而窃火者靠**交换 actor/target** 实现偷取 ⇒ 计价点在**被动侧**而不是 op 侧；「成功质疑」= **答错**（`passed=false`）而不是答对；「改判」= `modify_judgement` 而不是 `reroll`。
- **计数写入要共用一份实现**：新增 `engine/core/counters.ts`（`bumpCounter` / `counterPatch` / `bumpCounterOf`，支持负 delta 供复议回退）⇒ 避免每个写入点各写一遍「怎么加」。
- **盲审的「建议修法」要对照既有裁定再采纳**：盲审建议「在 `certifyAnswer` 加引擎级幂等守卫」⇒ 但既有裁定明写「去重由粗筛承担」（`legal.ts:142-143`）且门禁层**登记**了「UI 比引擎严」的口径 ⇒ 照建议改会**推翻既有裁定并让门禁变红** ⇒ 改为**计数侧幂等 + 改判回退**（同样消除虚高、零冲突）。⇒ **审阅意见 ≠ 裁决，既有裁定优先。**
- **盲审指出的「测试名承诺 ≠ 断言体」**：我那条用例名写着「复议推翻 ⇒ −1」而断言体只测 `+1` ⇒ **名实不符**且掩盖了零覆盖 ⇒ 已改名并补真实流程断言（E6）+ 专属 mutant（§6.1）。
- 已写入 `docs/沉淀/经验教训索引.md` **E111 / E112**；Agent Memory 同批沉淀 2 条。
