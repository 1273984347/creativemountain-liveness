# B12 — 被动补完（7 个身份被动的消费点）执行记录

## 1. 目标

为**剩余 7 个身份被动**补齐消费点。此前这 7 个被动的 op 只出现在主题包里，
引擎里**没有任何消费点** ⇒ 「只写不读」死机制：机制看着实现，实际永不触发。

| 身份 | 被动 op | B12 前 |
|---|---|---|
| 开拓者 | `move_forward` | 只在卡牌/指令骰里被调用，**自身无触发点** |
| 匠师 | `equip_card` | 同上（且 op 与文案不符） |
| 观星者 | `peek_deck` | 同上 |
| 仲裁者 | `extra_vote` | ✅ **已实现**（B10 收尾②：山议计票读 `flags.extraVotes`） |
| 守夜人 | `shield` | 同上 |
| 窃火者 | `transfer_resource` | 同上（且 `target: 0` 是**占位**） |
| 织梦者 | `set_die_result` | 同上（且 `value: 10` 对 6 面骰是**非法点数**） |
| 山主 | `certify_free_pass` | 同上（`flags.certifyFreePass` **无消费点**） |

## 2. 裁定（用户拍板，三处 op 与文案不一致）

| # | 裁定 | 理由 |
|---|---|---|
| ① | 匠师被动改用 **`create_card`**（真·免费造物，从造物牌堆取牌） | 与文案及规格 §6.5 一致；原 `equip_card` 是「把手牌移入装备区」 |
| ② | 守夜人以**主题包文案**为准 = **回合结束获得 1 点护盾**（自动生效） | 规格 §4.1 那张表头写着「特权（示例）」，主题包 `passiveText` 才是实际文案 |
| ③ | 织梦者改用 **`modify_judgement`** = **改写自己的险径判定为安全** | 与观星者「看牌堆顶」呼应（§3.4 险径判色）；原 `set_die_result{value:10}` 把骰子固定设为 10，对 6 面移动骰非法 |

## 3. 触发点设计（规格 §4.1 升级为**权威被动表**）

| 身份 | 触发方式 | 限制 | 引擎消费点 |
|---|---|---|---|
| 开拓者 | **自动**（行棋结算） | 每回合 1 次 | `turn-runner.performAction('move')` —— 经 `turn.moveBonus` **叠加**（`move_by_dice` 内部 `raw = position + roll + moveBonus`，故 bonus 必须在掷骰前加，否则「恰好够到峰顶」差一格） |
| 匠师 | **主动**（行事） | **每场 1 次** | `abilities.performAbility` → `create_card`（`counters.freeCreates` 计数） |
| 观星者 | **主动**（行事） | 每回合 1 次 | `abilities.performAbility` → `peek_deck`（牌面写入 `flags.peeked`，否则玩家看不到颜色 ⇒ 「提前知道险径」这条设计意图落不了地） |
| 守夜人 | **自动**（回合末） | 每回合 1 次 | `turn-runner.finishTurn` → `shield` |
| 窃火者 | **主动**（行事）+ **选目标** | 每回合 1 次 | `abilities.performAbility` → 以**目标为 actor** 反向执行 `transfer_resource`（复用既有 op，不新增算子） |
| 织梦者 | **主动**（行事） | 每回合 1 次 | 发动时挂 `flags.judgementModified`；**消费点** = `turn-runner.resolveTile` 的 hazard 分支（无论牌色都消费，否则标记无限留存） |
| 山主 | **自动**（进入待认证） | 每场 1 次（首次） | `certification.enterPendingCertification` 挂标记；**消费点** = `certification.certifyChallenge`（该质疑**视为签印**，仍照常扣 1 灵枢 ⇒ 成本对称） |

**次数闸门**：「每回合 1 次」用 `Player.turn.abilityUsedThisTurn`（**可选字段**，回合末清零）；
「每场 1 次」用 `Player.counters.freeCreates`（本局累计，不清零）。

**授予**：分配身份时把被动规格写入 `player.flags.passive`（`engine/core/setup.ts`）⇒ 引擎按 **op** 分发，
**主题化友好**（不同主题的同一身份用不同 op 也能正确工作）。

## 4. 顺带复核更正：造物牌 id **不是**冲突

B12 曾判定「16 张造物牌全部与普通牌撞 id ⇒ 需加 `mk_` 前缀隔离」并实施 —— 
**主题包校验器直接判红**：「造物牌引用了不存在的卡牌」。
⇒ 真相是：**造物牌的 `cardId` 本就必须是普通牌的引用**（造物 = 指定某张普通牌作为可造之物，
校验器强制这条）⇒ 所谓「id 冲突」是**设计意图**，不是缺陷 ⇒ 已撤销改名（主题包校验 4 套全 PASS）。

> **教训**：动手改「看起来是 bug 的重复 id」之前，先看**校验器的判据** —— 它往往编码着设计意图。

## 5. 可达性证据（B12 的核心验收）

模拟器 AI 会**偶尔发动**被动（发动**占用本回合行动**，规格 §3.1 行动三选一）；
所有被动触发都写 `[被动:<op>]` 前缀日志（主动型与自动型**同格式**）⇒ 统计口径统一。

**800 局（8 人档）触发统计**：

| 被动 | 触发次数 | 触发过的局数 |
|---|---|---|
| 开拓者 · 首次移动 +1 格 | 732 | 732 |
| 匠师 · 免费造物 | 314 | 314 |
| 观星者 · 看牌堆顶 | 299 | 299 |
| 守夜人 · 回合末护盾 | 10447 | 800 |
| 窃火者 · 偷灵枢 | 294 | 294 |
| 织梦者 · 改险径判定 | 506 | 327 |
| 山主 · 免质疑 | 222 | 214 |

⇒ **7 个被动全部在真实对局中触发**（此前一个都不触发）。
回归测试 `balance-regression.test.ts` 断言这一条（读模拟报告的被动触发统计）——
只测「执行该算子后状态变了」**不够**，那证明不了链路通。

## 8. 方法论教训（跨项目通用）

**教训①：只写不读的算子 = 死机制。** 主题包里有 op、引擎里也注册了 op，**不等于机制活着** ——
必须 grep 到**消费点**，并写一条「该机制在真实对局中可达」的断言（触发次数 > 0）。
本批把这 7 个被动的触发次数从 **0** 变成 **数百次**，机制才真正上线。

**教训②：动手改「看起来是 bug」之前，先看校验器的判据。**
造物牌 id 与普通牌同名 —— 我判定为「id 冲突」并实施改名，校验器直接判红：
**造物牌本就必须是普通牌的引用** ⇒ 是设计意图，不是缺陷。

**教训③：跨会话协作要先查工作区。** 本批开工时发现工作区有**另一个会话**的未提交改动
（`victory.ts` 注释修正 + 新增回归锁 + 产品文档）⇒ 避开那两个文件（不改其历史行、不代提交），
用**显式 pathspec** 只提交本批自己的文件。
