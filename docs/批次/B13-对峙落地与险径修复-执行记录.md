# B13 — 对峙落地 + 险径修复 执行记录

## 1. 目标

一并处理 B12 遗留的两个同类漏洞（与「7 个被动只写不读」性质相同）：

| # | 漏洞 | 性质 |
|---|---|---|
| ① | **对峙流程未落地** | 规格 §3.3 专门写了一整节（红>黑 → 同色比 rank → 平局 → 胜负），引擎里只有**一个无人调用的半成品 op** `compare_cards` ⇒ 对峙**至今不可达** |
| ② | **险径红牌不移除牌堆顶** | `resolveTile` 的 hazard 分支红牌直接 return、**不移除** ⇒ 牌堆顶永远不变、每次经过险径都是同一张（黑牌分支却会移除 ⇒ 牌库行为前后不一致） |

附带发现：`compare_cards` 的**语义也与规格不符** —— 它把**对手的牌抢过来**，
而规格 §3.3 规定「胜者把败者**推后 1 格**，败者**抽 1 张牌**；胜者不获额外收益」。

## 2. 裁定（用户拍板）

**亮牌方式 = 双方各自选牌、选完才同时揭晓**（规格 §3.3「双方同时亮 1 张手牌」的完整实现）
⇒ 需要对峙面板 + 状态机 + **回合阻塞**。

## 3. 引擎实现

### 3.1 新增 `engine/core/duel.ts`（对峙的权威实现）

| 函数 | 作用 |
|---|---|
| `compareCards(a, b)` | 纯比较：颜色（红>黑）→ `rank` 数值 → 平局 |
| `startDuel(state, a, b)` | 进入待决对峙；**任一方手牌为空 ⇒ 直接判负**（不进待决） |
| `submitDuelCard(state, seat, cardId)` | 锁定一张亮牌（**对对方不可见**）；两人都锁定 ⇒ 一次性揭晓结算 |
| `autoResolveDuel(state)` | **自动为双方选牌并结算**（红优先、同色 rank 大优先）—— 给 AI / 教学演示 / 脚本 / 测试用 |
| `isDuelParticipant` / `duelOpponent` / `duelPicked` | 供 UI 判断参与状态与已否锁定 |

**结算语义（严格按规格 §3.3）**：

- 分出胜负 ⇒ **败者推后 1 格 + 抽 1 张牌**；**胜者不获额外收益**（不拿对手的牌）；
- 两张亮牌**公开留场**（进 `State.publicCards`，**不回任何人的手牌**，round 末清空）；
- **平局** ⇒ 双方**均不后退**、**各弃 1 张**（即各自的亮牌弃掉、**不公开留场**）——
  B13 裁定，消除原文第 3 条与第 6 条的张力；
- 任一方**手牌为空** ⇒ 该方**自动落败**（推后 1 格、不抽牌）。

### 3.2 State 与流程

| 项 | 内容 |
|---|---|
| `State.duel` | 待决对峙（双方座位 + 各自已锁定的亮牌） |
| `State.publicCards` | 本 round 公开的亮牌（round 末清空） |
| `Player.turn.finished` | **本手番是否已结算**（可选字段）：结算后进入对峙 ⇒ **暂停推进**，待双方选完牌再调 `advanceTurn` 时**跳过重复结算**、直接推进 |
| `resolveTile` | 地形结算与**对峙检测分离**（见 §5 教训②）；落点与其他存活玩家同格 ⇒ 进入对峙（待认证锁定者不参与） |
| `advanceTurn` | 对峙未结算 ⇒ **回合阻塞**（直接返回，不推进） |
| round 末 | 公开亮牌离场（`publicCards` 清空） |

### 3.3 UI

对峙面板（行动区）：显示「对峙：座A vs 座B」+ 当前操作者的状态（该你锁定 / 已锁定待对方 / 双方已锁定）；
选牌方式 = **点击手牌中的一张**；玩家行加「对峙」标记。

## 5.5 浏览器端到端（对峙）

**为什么不用内置浏览器手点**（实测踩坑）：① UI 的 seed **固定** ⇒ 同一局轨迹可复现，靠随机行棋撞对峙既慢又不可靠（实测 11 轮未命中）；
② `inspect` 每次返回整页 81 个元素的 JSON ⇒ 连续调用直接把会话算力预算打爆（两次 `compute_budget_exceeded`）；
③ 坐标方案不可靠 —— 布局随人数/手牌数量变化。

**方案**：改用项目**自带**的 Playwright（`tests/e2e/duel-e2e.mjs`，`npm run test:e2e`）：
遍历 4 套主题 × 2 档人数，每局最多 60 步轮流移动两个座位 ⇒ **第 2 次开局即命中对峙**。

## 7. 方法论教训（本批三个自踩的坑）

**教训①：用 `write` 覆盖「含其他内容的文件」⇒ 静默清空。**
我为替换 `resolveTile` 一个函数而 `write` 了整个 `turn-runner.ts` ⇒ 其余内容全被清空（工具提示仍是「成功」）。
⇒ **局部替换一律用 `edit`**；`write` 只用于新建文件。

**教训②：早 `return` 的分支会让后续逻辑永不执行。**
把「地形结算」与「对峙检测」写在同一个 `switch` 里，而 `boon`/`hazard`/`peak` 分支都 `return`
⇒ 落到这三类格子时**对峙永不触发**（自己引入的 bug，测试立刻抓到）。
⇒ 同一函数里的多个职责要么**分离成两段**（先算地形、再查对峙），要么让所有分支走同一条出口。

**教训③：「未选牌」与「无牌可选」是两件事。**
自动落败分支最初用 `pick === undefined` 判「无牌可选」⇒ 空手方**没被判负**、反而判了另一方。
⇒ 状态判据要用**各自的语义字段**（手牌长度 vs 选牌字段），不能复用同一个 `undefined`。

**教训④：会阻塞流程的机制，必须给所有调用方一个统一出口。**
对峙阻塞回合推进 ⇒ 任何自己驱动对局的调用方（测试、脚本、AI）不处理对峙就会**卡死**
（实测：昼夜分支因此不可达，测试红）。⇒ 引擎层提供 `autoResolveDuel`，调用方统一组合。
