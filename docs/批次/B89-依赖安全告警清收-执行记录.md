## 5. 验收

- **告警归零的本地前提**：4 条告警对应的实际安装版本全部 ≥ 各自修复版本（§4.2）⇒ 平台复扫时应全部转 closed（**待推送后复扫确认**，见 `L-B89-1`）。
- **根仓门禁**：`node tools/gate.mjs` ⇒ **14 门全绿**（门数不变，本批未新增门禁）。
- **host 三引擎**：`HOST_WALKTHROUGH_BROWSER=chromium|firefox|webkit` 各跑一次 ⇒ 三者 **exit 0**、`failures=[]`、`knownErrors=[]`。
- **产物等价**：单文件 HTML 的 SHA256 与字节数与升级前基线**完全一致**。
- **变更面**：根仓 lock 只增 1 个平台包；host lock 只动 3 个目标包 + 1 个必然连带 ⇒ **无无关 churn**。
- **文档口径**：`node tools/doc-sync.mjs` ⇒ PASS；批次导航复算 ⇒ 总览 / 小节标题 / 实际行数 / 目录文件数**四者互洽**；沉淀索引「E 行数 ≡ 分类声明之和」成立。

## 6. 复盘与经验沉淀

### 6.1 沉淀

- **E148**：**「有安全告警」不等于「能被自动工具修复」** —— 依赖树里的告警有三种可修性：① 直接依赖可自升；② 传递依赖且**上游已修** ⇒ Dependabot 可自动出 PR；③ 传递依赖且**上游未修**（上游最新版仍声明旧的版本区间）⇒ **任何自动工具都修不了**，此时唯一可行路径是本仓 `overrides` 强提（或等上游）。判据要先问「**谁能提供修复版本**」，而不是先问「告警能不能消」。
  ⚠️ 实测后果：第三种情况下 Dependabot 的 security job 会**每周固定失败**（exit 1，日志写「latest possible version … earliest fixed version …」）⇒ 那是**配置与上游状态的结果**，不是本仓配置错。
- **E149**：**跨 major 强提传递依赖，「装得上」不等于「可用」** —— `npm install` 成功、`npm ls` 无 invalid，只能证明**解析**层面成立；真正的判据是「**下游库实际怎么用它**」：① 读下游库对该依赖的 import 形态（本次：`diff` v8 仍导出 `diffLines`，sparkdesign 的命名导入兼容）；② 跑下游的**端到端实测**（本次：host 走查三引擎 `knownErrors=[]`）；③ 比对**产物哈希**（本次：根仓产物逐字节相同）。三条都过 ⇒ 才能判定「零影响」。
- 复用既有教训：**E139**（工具返回成功 ≠ 落盘 ⇒ 所有插入改写都用 `assert` 锚点 + 回读校验）、**E142**（守卫要比对真正被使用的常量 ⇒ 本批比对的是**实际解析版本** `npm ls`，不是 `package.json` 里写的区间）、**E143**（改完立刻跑 ⇒ 升级后立即跑门禁与三引擎走查）。
